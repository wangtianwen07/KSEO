## 长请求不结束时，先区分活性与完成

观察：任务多轮报告 LongBenchv2 完成进度暂未变化，但服务输出 token 总数持续增加，进程仍在且服务健康。随后两个长请求产生完整终态。

坑：把完成样本数长时间不动当成卡死，可能导致中断仍在执行的请求；仅凭健康接口又不能证明目标请求一直前进。流式分片数也不等于模型 token 数。

做法：关联进程身份、目标请求/流、逐请求原始事件及时间戳；服务级累计 token 增量只作辅助。保存终态前，不把请求写成完成。先核对冻结的上下文余量与输出预算，评估长尾时间；不得为了缩短等待临时修改正在执行的合同。

## `length` 终止、原始响应完整与答案正确分别判断

观察：来源任务报告两个请求各生成 1,031,643 token，总 token 各为 1,048,576，结束原因为 `length`。任务中的审阅脚本核对了原始 SSE 的 `[DONE]`、usage、finish_reason，以及拼接正文与 attempt 正文的 SHA256 一致；完成 token 等于该题输出预算。

坑：把达到预算称为答案正确，或把百万级长输出解释为长输入吞吐提升。两条请求的一致性也不能外推整个 LongBenchv2。

做法：分别保存传输完整性、预算一致性、答案提取及评分结果。`length` 按冻结协议处理，不能仅由该标记断言质量通过或服务故障。LongBenchv2 从最终正文提取选项，继续保留完整 525 分母及原顺序。具体规则见 [最终精度合同](final-accuracy.md)。

来源产物定位（相对执行任务的产物根目录）：`discovery/longbench-long-output-partial-review-v1.json`、`accuracy-runs/baseline-new/longbench_v2/<sample_id>.attempt.json` 及对应 `.sse.jsonl.gz`。本页不填造未取得的文件 hash。

## 源码存在重放路径，不代表当前请求正在重放

补充来源：执行任务轮次 `01a1a973-e0e9-7560-8250-b2fd9deed6bd` 的阶段报告。任务报告确认源码存在“重排后重放旧 token、校验但不重复发送”的机制；同时明确当前请求是否处于该路径尚无直接证据。后续轮次 `01a1a975-82a9-7ca1-ab76-a1e24a3519be` 报告 LongBenchv2 已落盘 142/525、两个请求未结束，进程存活且 KV 池占用变化；该数字仅是当时快照。

坑：以“没有新文本 + 源码有重放分支”直接断言当前正在重放，或以 KV 池变化证明某个请求的有效生成进度。源码可达性、服务活性、请求级因果证据必须分开。

做法：需要同一请求的调度事件、重排/重放标记、旧 token 校验位置及时间关联才能判断具体状态。缺少这些事件时只记录“原因未确认”，不把推测写成根因，不重复发起同一 GPU 实验。

## 阶段报告中的优化失败与工程经验

以下内容来自工作区 `artifacts/GLM53-KSEO-优化尝试汇总-20261105.md`，整理时文件 SHA256 为 `ccee049caeec34f92c543a6110bb948114cdcde2f296e07ec9120c93f0e7f72e`。此 hash 仅标识读取的汇总文件，不代替远端实测产物 hash；本页未独立重算该报告全部数据。原报告位于仓库外，公开读者不能仅靠本页复现实验。

### MoE 夹具必须覆盖共享专家槽

报告观察：早期合成夹具只覆盖八个路由专家，漏掉最后的共享专家槽；旧八槽微测明确作废，改为九槽重测。更正后的夹具覆盖 prefill/decode、多种行数及均匀/集中路由。

经验：先从真实调用核对专家数、槽顺序、共享专家、权重布局与累加顺序，再冻结 oracle。合成输入的数值通过只能证明该夹具覆盖范围。发现缺槽时，应撤销依赖该夹具的候选筛选结论，并明确其他证据是否受影响，不能把整次任务一概判为有效或无效。

### 局部加速、资源指标与 E2E 收益不能互相替代

报告观察：Q4 三个形状微测出现约 1.17、1.09、1.48 倍加速；集成候选 c010 的十二场景试测仍未全面达标。MoE split-N 把寄存器数从 118 降至 80，也未获得稳定整体收益。c023 分块归并原型通过十个案例的逐位检查，但报告中的 2048 行集中路由从 12.59ms 变为 17.87ms，未集成。

经验：资源数下降只是机制证据，不能直接算收益。候选先做完整调用的交错对照，再回到全负载 TTFT/TPOT；保留单场景回退与失败请求。profiler 插桩轮次只作诊断，正式计时另测。发生基线漂移时，记录原始前后对照，不能择取有利基线宣称稳定改善。

产物定位：`trials/c010-pilot-v3`、`discovery/moe-v2-final-decisions.json`、`kernel-search/staged-combine-results/validate`。

### 先校验实际后端参数，再启动昂贵实验

报告观察：搜索草案曾含环境变量拼写、HC 布尔参数及投机策略缩写错误，在运行前通过实际后端解析器修正；二十二组准备方案通过解析检查，但尚未执行完整搜索。

经验：将参数解析与最终生效配置核对放在 GPU 实验之前；未知参数、忽略的环境变量和默认值回退均须显式处理。解析通过仅代表语法/支持范围检查，不代表配置已部署、正确性通过或性能有益。

### 适配器模块名可能遮蔽 Python 标准库

报告观察：适配目录中的 `platform.py` 遮蔽标准库，已修正。当前公开知识库尚无对应 traceback 或独立复现产物，因此不推定具体导入链。

经验：适配器避免使用 `platform.py`、`json.py` 等标准库同名文件；在与真实启动一致的工作目录及解释器下检查导入模块的 `__file__`。只在仓库根目录通过测试，不能证明远端入口没有模块搜索路径问题。

### 源码一致不等于运行环境一致

报告观察：两机镜像摘要不同，另行核对的 429 个 TensorFold 源码文件一致；实验按源码版本隔离 CUDA/Triton 编译缓存。

经验：镜像、源码、实际载入模块、编译产物与配置分别记录身份。源码比对不能抹平驱动、依赖或镜像差异；缓存隔离也不能替代实际加载产物核验。恢复脚本准备完毕与实际恢复验证分别留证。

## Profiler 的内核累加、活动区间与关键路径分别计算

补充来源：工作区 `artifacts/GLM53-推理瓶颈核对-20261105.md`（SHA256 `84bbab07699903137311c7f857b169de4a9cb83b4af6188bfa8d814d12487bfd`）、`artifacts/GLM53-profile-bottlenecks-verified-20261105.json`（SHA256 `67ef6177affb4151afe5f5cb0c88b1feb77e83ee4afa5731d65fe657f9371471`）。报告绑定既有 rank0 SQLite hash `f354d86c0a437e961fbfd5d5b55affe7510ad5660c858071a0c6524e96d0659b`；本页独立核对了本地 JSON 的分类加总及报告数字，未在此取得 SQLite 重算，不将报告身份提升为原始数据独立复现。

观察：四个捕获范围中 MoE 占 GPU kernel duration 累加的约 40.26%—51.24%，MoE 与 Q4 合计 58.84%—66.24%。ShareGPT C1 近似 prefill 范围的通信内核累加约 18%，但按活动区间并集扣除与非通信内核重叠后，仅通信活动约占该 span 的 4.90%（2K）与 4.42%（8K）。无内核活动约为 0.143% 与 0.635%。

坑：多 stream 的内核 duration 可以重叠，累加分母不等于 wall time；“仅通信活动”也不自动等于可消除关键路径。微小空闲间隙不能证明 CPU 无瓶颈，内核名称带 `dec_kernel` 也不能证明它只用于 decode。

做法：同时报告 duration 累加、区间并集、阶段边界和 rank 覆盖。该报告只覆盖 rank0，近似 prefill 从首个 GPU kernel 到最后一个 prompt MoE kernel，不是精确 TTFT 边界；混合 prefill、投机验证和生成的范围不能直接归为 TPOT。热点排序可用于安排实验，带宽/计算屋顶和双 rank 因果关键路径仍需进一步证据，正式收益另用无插桩 E2E 对照验证。

### CRLF 源码与 LF 补丁：完成状态可能掩盖分支未采用

本次独立 CPU 复现：在持久产物目录 `artifacts/knowledge-agent-diagnosis-20261105` 运行 Agent 示例，最终状态为 `COMPLETED`、最佳分数 105.3；但 Kernel 候选记录为 `Git 操作失败: error: patch failed: demo_kernel.py:1 / patch does not apply`。这不是 Kernel 性能不达标，而是补丁未能应用。

直接字节检查：候选基线 `demo_kernel.py` 的八个换行全部为 CRLF，生成的 `patch.diff` 十个换行全部为 LF。在原候选基线上重跑 `git apply --check` 失败；复制同一源码到隔离控制目录、仅把 CRLF 转成 LF 后，同一补丁的 `git apply --check` 返回 0。控制实验没有修改任务源码、合同、Validator 或 GPU 服务。

后续针对性验证：复制当前工作区 `src`/`tests` 到 Linux 原生临时目录，仅对 `.py`/`.json`/`.md` 文件规范为 LF，在副本中运行上述四个失败用例，4/4 通过（10.607s）。日志定位为工作区 `artifacts/knowledge-lf-control-tests-20261105.log`。本实验同时改变了换行和文件系统位置，不是其余三个 pipeline 用例的单变量根因证明。

结论边界：已确认这个 Agent 示例的补丁应用失败与换行不匹配有关；另外三项在隔离 LF 副本中通过，但其唯一根因仍未逐一闭环。没有修改公开框架实现，也未在该副本重跑全量 172 项，因此不宣称框架修复或全量回归通过。

经验：跨 Windows/Linux 的实验必须冻结换行策略与实际源码字节身份，先检查补丁可应用性。不能用总状态 `COMPLETED` 证明每个优化分支都执行成功；应审阅候选拒绝原因、是否产生预期补丁和最终采用的产物。任何换行规范化都应在冻结基线前明确进行，不能运行后静默改变已绑定身份的候选。

## 短回归另建基线，不能借用完整评测成绩

来源：同一执行轮次的后续命令输出确认短筛选合同已冻结、语法检查通过，64 个固定样本、最大输出 4096、并发 4；启动输出说明顺序为新短基线 64 题，再跑冷前缀性能试测 126 请求。任务说明该短协议无重试。此时只有冻结及启动证据，没有短基线分数或候选通过结果。

经验：输出预算和样本集合变化后，先独立测新短基线，再让候选使用相同短协议；旧完整 GSM8K 分数不能直接成为新子集阈值。样本清单及顺序应在候选结果出现前冻结，避免挑容易题或按候选错题调整集合。逐位数值、短精度及性能各保留独立结论，短回归通过不等于四套全量精度通过。

范围：64/4096/C4 是当前任务的筛选选择，不是 KSEO 的通用模型默认，也不修改旧评测记录或最终质量合同。此处未取得短合同 hash，不能声称已独立审阅全部样本及请求身份。

后续生成审计来源为轮次 `01a1a996-b67d-75a0-8779-433cc736a1cd` 的输出：64 条 finish_reason 均为 `stop`，最大观察输出 270 token、触及预算数为 0，所有请求预算均为 4096。该证据支持“这次短基线没有触及输出上限”，不能外推到候选、全量 GSM8K 或长上下文数据。设定上限后应核对实际终止分布与逐题 usage，而不能凭预算值推断是否截断；没有截断也不能证明答案正确或子集具有全量代表性。

## 短精度成功、性能连接失败与队列退出分别归类
